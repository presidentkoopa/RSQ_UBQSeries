# RSQ FnF (Flash and Flare): findings from reading the code (2026-11-27)

Read at commit 50f608e63. Every ZScript file the mod includes was read whole (zscript.txt and the eleven files under
`zscript/rsqff/`), with CVARINFO, MENUDEF, MAPINFO, SNDINFO, VOXELDEF and the head of the two MODELDEF lumps. There is
no KEYCONF, LANGUAGE or GLDEFS. Nothing was run: no rig, no headset. Each finding is a question for the owner. Nothing
was changed.

Paths are inside `FlashFlare/` unless they start with another folder. `handler.zs`, `torch.zs`, `burn.zs`, `fire.zs`,
`geo.zs`, `items.zs`, `battery.zs` and `stowed.zs` are in `zscript/rsqff/`. "Old README" is `FlashFlare/README.md` as
committed at 50f608e63 (`git show 50f608e63:FlashFlare/README.md`).

Ordered by what a player would meet first. Wording and comment mismatches are at the end.

**The keys plan (design/KEYBINDS_PLAN.md:6) against the code:** the plan says this mod has no keys, and the code has
none: no KEYCONF, no alias, no bind. Two inputs are read and neither is eaten: the off hand's grip by raw key code
(`rsqff_keys_off`, handler.zs:183-197) and the off hand's trigger (the off hand attack button, and any key whose bind
text contains `+oh_attack`: handler.zs:174-178, torch.zs:291-292). Main-hand fire, alt fire, Use and the sticks are
never read. Brutal Doom's own Flashlight key is neither read nor replaced.

**What a player can never reach:** the code paths for a player out of VR (handler.zs:414, torch.zs:461-465) can only be
reached by typing this mod's network events in the console, because every take, light, throw and switch returns first
when the player is not in VR (handler.zs:484, torch.zs:661). The new README says so under Limits. The other things a
player would not find are F3, F7, F8 and F9 below.

## F1: The flick that lights a flare can be missed unless it also goes forward
- Kind: possible bug
- Where: handler.zs:516 (the strike reads `Peak`), handler.zs:539-541 (the test: down speed at least 1.4 m/s and at least 0.6 of the whole), handler.zs:721-723 (`Peak` returns the fastest window that goes "ahead"; the fastest of all only when no window at all goes ahead); handler.zs:36 (the code's own note on this 11-22 change: "Code only, not run")
- What the code does: the strike is tested on the one window `Peak` returns. Since 11-22 `Peak` prefers a window whose motion across the ground is within 60 degrees of where the head faces. A flick straight down has almost no motion across the ground, so whether it counts as "ahead" depends on a tiny sideways drift. If it does not, and any other window in the same 7 tics drifted forward even slightly, that slow window is returned and the strike test fails.
- Why it looks wrong: the throw's "ahead" rule was written for throws, and the strike shares it by accident. A player flicks down hard and the flare sometimes lights and sometimes does not, with no pattern he can see. With Light It By: Either (default) the trigger still lights it, which would hide the fault; with Light It By: Strike it is the only way.
- Sure?: likely. Certain about the code; how often a real wrist hits it needs a headset: Light It By: Strike, Debug Log on, twenty flicks straight down, count the "RSQFF strike" lines.
- Fix A: the strike uses the fastest window of all (give `Peak` a flag, or return `bestAny` as a third value) (about 5 lines, 1 file).
- Fix B: the strike tests the largest downward speed of any window in the 7 tics, not one picked window (about 8 lines, 1 file).
- Or intended: the README row says: "flick the off hand down and away from you".

## F2: A throw that does not go where you are looking can be read as slow, and the flare stays in the hand
- Kind: possible bug
- Where: handler.zs:712 (ahead is measured from the pawn's angle, which in VR is where the headset faces), handler.zs:721-723 (`Peak`), handler.zs:567 (under 2.2 m/s the let-go does nothing)
- What the code does: the same rule as F1, for the throw. Throw sideways, behind you, or forward while looking away, and the throw's own windows are not "ahead". If any other window drifted forward a little, that drift is the speed tested: under 2.2 m/s, so nothing happens.
- Why it looks wrong: the comment (handler.zs:38-39) promises "the fastest of all" for a sideways flick; the code gives that only when nothing at all went forward. The player lets go mid-swing and the flare is still in his hand.
- Sure?: likely. Certain about the code; a headset settles how often: look 90 degrees left, throw hard straight ahead of the body, ten times, Debug Log on (it prints the swing speed at each let-go).
- Fix A: use the ahead window only when it is at least half as fast as the fastest window; else the fastest (2 lines, 1 file).
- Fix B: test "is it a throw" against the fastest window of all, and use the ahead rule only to pick the direction (about 4 lines, 1 file).
- Or intended: the README row says the throw must go where you look.
- Note: the same code is in RSQ Grenade (its findings F2) and RSQ ShieldSaw. One answer can serve all three.

## F3: A let-go too slow to throw gives no sign, and a lit flare cannot leave the hand any other way
- Kind: other
- Where: handler.zs:564-572 (trigger let go: thrown at 2.2 m/s or more, else `return`); handler.zs:574-578 (the grip does nothing to a lit flare); handler.zs:566 (the only output is a debug line)
- What the code does: a lit flare leaves the hand only by a throw (trigger held, then let go at 2.2 m/s or more), by burning out (60 seconds), or when something else takes the off hand. A slower let-go does nothing: no buzz, no sound. A flare lit by the flick has never had its trigger pulled, so the player must think of squeezing the trigger before he can throw at all.
- Why it looks wrong: a player who lights a flare and then wants his off hand back has no way to learn why the flare will not go. Nothing tells him the let-go was read and was too slow.
- Sure?: certain about the code. Whether players get stuck is the owner's call (he chose "Trigger only" on 11-06).
- Fix A: a short low buzz on a let-go under Throw Speed, so the hand feels "read, too slow" (2 lines, 1 file).
- Fix B: a toast once per map on the first too-slow let-go: "Swing and let go to throw" (about 6 lines, 1 file).
- Or intended: the README keeps its limit: "A let-go slower than Throw Speed gives no sign."

## F4: The flashlight does not wait for the engine's two-hand steadying as the flare does
- Kind: possible bug
- Where: torch.zs:304 and :309-325 (the take raises the flashlight at once); handler.zs:374-382 (the flare's take waits, with the reason written out: the engine hides what the off hand holds while it steadies the gun, and "an off-hand weapon raised meanwhile can arrive invisible")
- What the code does: the flare's take is held until the steadying ends. The flashlight's take has no such wait. Without the Tactical Rig its clip is on the chest, where the off hand can be within the 0.5 m of the main hand that the note says starts the steadying.
- Why it looks wrong: by the code's own note, a flashlight taken with the hands close could come up unseen: the beam shines but no flashlight is drawn in the hand.
- Sure?: unsure. A headset settles it: no Rig, gun held at the chest, grip at the clip, look at the off hand.
- Fix A: give the flashlight's take the same wait (a `takeWant` and the same test in its `Keep`) (about 12 lines, 1 file).
- Or intended: the README says nothing more; the clip is far enough from the gun hand.

## F5: Old README says a flare burns at the world's speed in slow motion; the code slows only a burning monster
- Kind: README claimed, not in code
- Where: old README, "Plays well with": "RSQ SlowMo: a flare burns at the world's speed."; fire.zs:112-128 (the monster's burn asks RSQ SlowMo for "scale"); burn.zs:87-91 (a flare's burn counts one tic every tic and asks nothing); SlowMo/zscript/rsqsm/clock.zs:1298 and :1316 (SlowMo's rule: a class named RSQ* runs in real time unless listed, and of this mod it names only RSQFF_OnFire)
- What the code does: in slow motion a burning monster burns on the slowed clock. Nothing in this mod slows a flare's flight or its 60 seconds.
- Why it looks wrong: a flare thrown in slow motion would fly and burn at full speed while RSQ Grenade's thrown grenade slows. The old README's line reads as if the flare slows.
- Sure?: likely. Certain about this mod's code; that SlowMo leaves the flare alone rests on SlowMo's own rule at the lines above. A rig test settles it: throw a flare during a slow-motion pulse and time its flight.
- Fix A: the thrown flare asks RSQ SlowMo for "scale" and runs its flight and burn by it, as the grenade does (about 15 lines, 1 file).
- Fix B: add RSQFF_Flare to SlowMo's slowed list, if its state-driven rule fits (1 line in SlowMo; the burn clock would still be real time).
- Or intended: the README row says: "A monster's burn runs at the world's slowed speed" (the new README already says only this) and a limit says a flare does not slow.

## F6: After a level change the off hand does not get back the weapon it held before the flare or flashlight
