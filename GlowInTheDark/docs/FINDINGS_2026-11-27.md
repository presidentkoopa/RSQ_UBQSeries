## F1: What it needs to load: its files say nothing else, and never darkdoomz.pk3 with it. The reported failure without DarkDoomZ does not match the files on disk
- Kind: other
- Where: ddz.zs:23, :43, :58-64 (ddz_* used as bare names); CVARINFO.ddz:9-16 (all eight are defined in this mod); CVARINFO.ddz:6-7 and CREDITS.txt:65 (do not load darkdoomz.pk3 too); tools/build_all.py:59-61 (CVARINFO.ddz and MENUDEF.ddz are packed into RSQ_GlowInTheDark.pk3); MAPINFO.txt:3
- What the code does: every ddz_* name in ddz.zs is defined by this mod's own CVARINFO.ddz, and the build ships it. A root file in a pk3 is named without its extension, so CVARINFO.ddz is a second CVARINFO lump. That is the engine's rule, and the series relies on it elsewhere: VisualRewards/pk3/MODELDEF.rsqvr, Grenade's MODELDEF.kinds.txt, FnF's MODELDEF.torch, weaponsets/WoS_Reloaded/CVARINFO.rsqbgn. The rig scripts load RSQ_GlowInTheDark.pk3 with no darkdoomz.pk3 (tools/rigtest/batch_final.sh:4, :40-42), and the old README's status reports those runs loading with no script error.
- Why it looks wrong: the brief reports "Unknown identifier" for these names whenever DarkDoomZ is not loaded. With the files as they are, that error could only come from a build or folder load that left CVARINFO.ddz out. With darkdoomz.pk3 loaded as well, the engine stops instead ("cvar 'ddz_mode' already exists"), which is the opposite need.
- Sure?: unsure. Certain that the names are defined and shipped here. Loading the built pk3 alone and reading the start-up log for "Unknown identifier" or "already exists" settles it.
- Fix A: move the eight ddz_* lines from CVARINFO.ddz into CVARINFO.txt, so no second lump can be left out (8 lines moved, 2 files; the clash with darkdoomz.pk3 stays).
- Fix B (as asked): read the eight settings with CVar.FindCVar instead of bare names in ddz.zs (lines 23, 43, 58-64; about 12 lines, 1 file). When ddz_mode is not found, the built-in darkness stands down (Mode 0, nothing written). It then compiles whichever lumps load. CVARINFO.ddz stays, so the clash with darkdoomz.pk3 stays.
- Fix C: let it run beside darkdoomz.pk3. Drop CVARINFO.ddz, apply Fix B, and stand the built-in handler down when DarkDoomZ's own handler class (DarkDoomZ_Handler) exists. The Darkness rows (MENUDEF.txt:121, :123, :236-248) then show DarkDoomZ's own settings. Without darkdoomz.pk3 there would be no darkness at all, which undoes the owner's 11-09 "bake it into GITD" (about 25 lines, 4 files).
- Or intended: the README says it needs nothing and that darkdoomz.pk3 must not be loaded with it (as written).
- Coordinator's note (2026-11-27): the one failing load was of a pk3 built by the repo root's build_all.sh, not tools/build_all.py; see whether build_all.sh packs CVARINFO.ddz.

## F2: After loading a saved game, every later darkness change darkens the map again on top of the old darkness
- Kind: possible bug
- Where: ddz.zs:22-35 (WorldLoaded has no saved-game test and re-reads every sector's current light as the "base" at :29-31); ddz.zs:66-76 and :125-131 (the old values come back with the save, so nothing is re-lit at the load itself); ddz.zs:79-117 (the next change writes every sector from that base). The mod's own handler.zs:208 does skip a saved game.
- What the code does: after a load, the base is the light that is already darkened. The next change of any darkness setting applies the darkness to it again. The changes include: a boss lowering the post-gain (react.zs:146), RSQ SlowMo's DOWN writing ddz_mode, Pair Darkness to Profile, and Glow In The Dark turned off. At defaults (Compress at Dismal, x0.625) the map goes to about x0.39 of its own light and stays there until the next map; another load and change makes it x0.24. Turning Glow In The Dark off after a load leaves the map darkened instead of giving back its own light.
- Why it looks wrong: playing alone, loading a save after dying is common, and a boss (Darken the Map is on by default) or a DOWN then makes the map darker than any setting asks for.
- Sure?: likely. Certain about the code; that the handler is saved and WorldLoaded runs on a load is the engine's rule (handler.zs:208 relies on the same). Rig test: load a save, note a sector's light, run `netevent rsqgd_test_mb 1` and then `0`, and compare.
- Fix A: in WorldLoaded, return before the snapshot on a saved game or a hub map you come back to (`if (e.IsSaveGame || e.IsReopen) return;` after the Lighting removal) (1 line, ddz.zs).
- Or intended: a README limit: "after loading a save, darkness changes add up until the next map". The code comes from DarkDoomZ as shipped (ddz.zs:8).

## Coordinator, 2026-11-27: F1's cause found
The repo root's `build_all.sh` packed only `CVARINFO.txt MENUDEF.txt` for this mod and left out `CVARINFO.ddz`,
`MENUDEF.ddz` and `KEYCONF.txt`, which `tools/build_all.py` packs. A pk3 built by `build_all.sh` therefore lacked the
eight ddz_* settings and failed with "Unknown identifier" (the one failing load this morning). Fixed in `build_all.sh`:
the three lumps are now packed. No code change in the mod.
