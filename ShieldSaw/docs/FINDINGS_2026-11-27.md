# RSQ ShieldSaw: findings from reading the code (2026-11-27)

Read at commit 1a846b85c. Every ZScript file the ShieldSaw includes was read whole (zscript.txt and the 13 files under
`zscript/ssq/`), with KEYCONF, CVARINFO, MENUDEF, MAPINFO, LANGUAGE, SNDINFO and the head of MODELDEF. Nothing was run:
no rig, no headset. Each finding is a question for the owner. Nothing was changed.

Paths are inside `ShieldSaw/` unless they start with another folder. `state.zs`, `guard.zs`, `disc.zs`, `pose.zs`,
`shield.zs` and `rsmenu.zs` are in `zscript/ssq/`. "Old README" is `ShieldSaw/README.md` as committed at 1a846b85c
(`git show 1a846b85c:ShieldSaw/README.md`).

Ordered by what a player would meet first. Wording and comment mismatches are at the end.

**The keys plan (design/KEYBINDS_PLAN.md:12) against the code:** the plan keeps one key, Draw / Put Back, and the code
has exactly one (KEYCONF.txt:10-11, no default bind). Throw Along Aim, Recenter Torso and Lock On (Hold) have no key
and no menu row. Locking is holding the trigger by default (CVARINFO.txt:174, state.zs:652), and a saved "lock key"
value is moved to the trigger once (state.zs:679). Two leftovers are F5.

## F1: The button that calls the disc home is also the trigger of whatever gun came back into the off hand
- Kind: possible bug
- Where: state.zs:846 (the recall), state.zs:1306 and state.zs:1271-1278 (the throw hands the off hand its earlier weapon at once); the file's own header, state.zs:6-7 and :21
- What the code does: the moment the shield is thrown, the off hand gets back the weapon it held before the shield (or the off hand saber, or BD22 VR's empty hand). While the disc is out, any press of the throw button (off primary fire by default) recalls it. Nothing checks what the off hand holds.
- Why it looks wrong: with a gun in the off hand, the first shot from it after a throw also turns the disc for home, before it has reached its rings. And a press meant as a recall fires that gun.
- Sure?: certain about the code. Whether it is felt needs a headset or rig test with a gun in the off hand before the draw (BD22 VR dual wield): throw at three rings, fire the off hand gun once.
- Fix A: recall on the press only when the off hand holds no gun (empty, RSQ_Hands, or the saber's off blade: the IsFiller test at state.zs:593), about 2 lines, 1 file. With a gun there, the Draw and Put Back key and the catch still bring it home.
- Fix B: recall on off secondary fire while the disc is out, whatever Throw Button says (about 3 lines, 1 file).
- Or intended: the README keeps its row: press off primary fire while the disc is out and it turns for home.

## F2: "Throw Button: Either" and "Rings Kept: 35" are changed back at the start of every map
- Kind: possible bug
- Where: state.zs:631-639 (MigrateLocks), state.zs:791 (run once per handler, guarded by mMigrated at state.zs:55); MENUDEF.txt:68 and :190 (Throw Button: Either), MENUDEF.txt:304 (Rings Kept, step 5, so 35 can be chosen)
- What the code does: on the first tic of each map the handler is new, mMigrated is false, and MigrateLocks runs: Throw Button 1 (Either) becomes 2 (Off Trigger), Rings Kept 35 becomes 175, Out of Sight Grace 14 becomes 105. It was written to move old defaults once, but nothing records that it has run, unlike the numbered moves in Migrate (state.zs:670-686, ssq_cfgver).
- Why it looks wrong: a player picks Either on the menu, it works until the next map, then the row reads Off Trigger again. The same for Rings Kept at exactly 35. (14 cannot be reached with the slider.)
- Sure?: likely. Certain about the code; that the handler is made again for each map is the engine's rule for a handler listed in MAPINFO's GameInfo. A rig test settles it: set Either, change map, open the menu.
- Fix A: move the three lines into Migrate as one more numbered generation (ssq_cfgver 7) and delete MigrateLocks and mMigrated (about 10 lines, 1 file).
- Fix B: delete MigrateLocks outright; the old defaults it moves date from before 10-27 (about 12 lines, 1 file).
- Or intended: none; the menu offers a choice the code undoes.

## F3: Use at the spot on your back is also a Use on whatever is in front of you
- Kind: possible bug
- Where: state.zs:828 and :837 (the draw reads the Use bit from the player's command), state.zs:867-877 (the only InputProcess; it never eats a key)
- What the code does: the draw and the put back read Use after the engine has taken it. The press reaches the game as a normal Use too.
- Why it looks wrong: standing at a door or a switch and reaching back for the shield opens the door or throws the switch. With Lock On With: Use, every lock hold is a Use on the world as well.
- Sure?: likely. A rig test settles it: stand at a door, hand at the back spot, press Use.
- Fix A: in InputProcess, eat the Use key going down while this machine's off hand is inside the grab zone, and send the draw as a network event (about 15 lines, 1 file; the way RSQ Wheel eats its presses).
- Or intended: the README keeps its limit: Use at the spot on your back is still a Use to the game.

## F4: "Lock On With: Trigger" is really "the Throw Button", and the tip says trigger
- Kind: menu disagrees with code
- Where: MENUDEF.txt:74 (the choice "Trigger"), MENUDEF.txt:187 (tip: "holding the trigger or Use"); state.zs:652 (any value but Use returns SecHeld, the throw button), state.zs:623 (Throw Button: Off Alt reads off secondary fire only)
- What the code does: with Lock On With: Trigger, the rings go on while the throw button is held. With Throw Button: Off Alt that is off secondary fire; holding the trigger then revs the saw and rings nothing.
- Why it looks wrong: only with a non-default Throw Button. The row says Trigger and the trigger does not lock.
- Sure?: certain.
- Fix A: rename the choice to "Throw Button" and fix the tip (2 lines, 1 file).
- Fix B: make the trigger always lock when the row says Trigger, whatever throws (1 line in LockHeld).
- Or intended: the README already says it: with Throw Button: Off Alt, off secondary fire rings and throws.

## F5: The console commands ssq_throw and ssq_recenter are still there after the keys pass
- Kind: other
- Where: KEYCONF.txt:8-9 (the two aliases; the note at :4-6 says they stay on purpose), state.zs:1632-1636 ("ssq-throw") and state.zs:1581-1585 ("ssq-recenter"); design/KEYBINDS_PLAN.md:12 ("Throw Along Aim goes", "Recenter Torso goes")
- What the code does: neither has a key or a menu row. Typed in the console (or bound by hand with `bind`), ssq_throw throws the shield along where you look and ssq_recenter recenters the body, or the Rig's body when the Rig carries the shield. TacticalRig/tools/rigtest/turnprobe/gen_rec_script.py:62 uses ssq_recenter. ThrowAlongAim itself is also what RSQ Accessibility's Shield Throw button calls (state.zs:1641), so that function stays either way.
- Why it looks wrong: the plan says both "go". A player can still bind a second throw by hand.
- Sure?: certain about the code. The question is whether "goes" meant the key or the command.
- Fix A: remove the ssq_throw alias and the "ssq-throw" branch (4 lines, 2 files); keep ssq_recenter for the rig probe.
- Fix B: remove both aliases and both branches, and point the rig probe at rsqtr_recenter only (7 lines, 3 files).
- Or intended: the README keeps its two rows: typed in the console, no key bound.
