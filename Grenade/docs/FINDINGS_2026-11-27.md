# RSQ Grenade: findings from reading the code (2026-11-27)

Read at commit 0252337bd. Every ZScript file the Grenade includes was read whole (zscript.txt and the files under
`zscript/rsqgn/`; of the generated data, `barrel_data.zs` only far enough to know what it is), with KEYCONF, CVARINFO,
MENUDEF, MAPINFO, DECALDEF, SNDINFO, TRNSLATE, RSQGCOFF and the head of the MODELDEF lumps. Nothing was run: no rig, no
headset. Each finding is a question for the owner. Nothing was changed.

Paths are inside `Grenade/` unless they start with another folder. `hand.zs`, `thrown.zs`, `kinds.zs`, `upg.zs`,
`barrel.zs`, `explosions.zs`, `flip.zs`, `bdlaunch.zs` and `rsmenu.zs` are in `zscript/rsqgn/`. "Old README" is
`Grenade/README.md` as committed at 0252337bd (`git show 0252337bd:Grenade/README.md`).

Ordered by what a player would meet first. Wording and comment mismatches are at the end.

**The keys plan (design/KEYBINDS_PLAN.md:7) against the code:** the plan keeps one key, Quick Grenade, and the code has
exactly one (KEYCONF.txt:3, :13, :14; no default bind). The same quick throw is also read from the engine button
+user1 (hand.zs:736); that is F10.

**What the code does not have at all:** catching or batting a grenade back, and an underhand roll. With no grenade in a
hand the hands are not read (hand.zs:883), and the only shaping of a throw is the 40 degree cap on its upward angle
(hand.zs:1074). The new README says both under Limits. If either was meant to exist, say so.

## F1: Squeezing the grenade with the grip held, before the pin is out, changes its type
- Kind: possible bug
- Where: hand.zs:901-903 and :916-920 (alt fire pressed with the pin in sends the type change); hand.zs:904-909 (the code's own note: with QuestZDoom's default mapping, grip and trigger together send alt fire and no fire); CVARINFO.txt:25 and :26 (both defaults on: alt fire cycles, All Types)
- What the code does: with the pin in, every press of alt fire on the grenade hand moves to the next type, unless the hand is at the mouth. The same file says a closed fist plus the trigger IS alt fire on a default QuestZDoom setup. So gripping and squeezing the spoon before taking the ring is an alt fire press.
- Why it looks wrong: the natural order is squeeze first, then pull the pin. A player who does that with the grip held throws an Impact (the next type after Frag), then an Incendiary, and so on, one step each grenade, and sees a type word pop each time without having asked for it. Without Gun Bonsai VR all nine types are owned, so this is the default.
- Sure?: likely. Certain about the code; that grip + trigger is alt fire is the code's own comment, not something this repo can show. A headset test settles it: pin in, hold grip, pull the trigger once, watch the grenade's colour.
- Fix A: cycle on a short tap only: alt fire pressed and let go within about 8 tics with the pin in. A held squeeze cycles nothing (about 10 lines, 1 file).
- Fix B: Alt Fire Changes Type off by default (1 line in CVARINFO, plus a one-time settings move like `rsqgn_feel`); the type is then picked on the Wheel's fan, or by turning the row on.
- Or intended: the README row says: "press secondary fire (or grip and trigger) with the pin in: the next type".

## F2: A throw that does not go where you are looking can be read as a slow one, and cooks in your hand
- Kind: possible bug
- Where: hand.zs:1133-1143 (Peak), hand.zs:165-169 (Ahead: within 60 degrees of where the body faces), hand.zs:975-978 (under 2.2 m/s the let-go cooks)
- What the code does: of the five 2-tic windows in the last 7 tics, the fastest one that goes "ahead" wins. The fastest window of all is used only when NO window goes ahead at all (bestM is still 0). "Ahead" is measured from the pawn's yaw, which in VR is where the headset faces.
- Why it looks wrong: throw sideways, behind you, or forward while looking off to the side, and the throw's own windows are not "ahead". If any other window in the same 200 ms drifted forward even a little, that small drift is the speed that is tested and thrown with: the let-go reads under 2.2 m/s, the spoon flies, and the grenade stays in the hand with 3 seconds left. The header comment (hand.zs:144-145) promises "the fastest of all" for a sideways flick; the code gives that only when nothing at all went forward.
- Sure?: likely. Certain about the code; how often a real arm hits it needs a headset: look 90 degrees left, throw hard straight ahead of the body, ten times, with Debug Log on (it prints the swing speed at the let-go).
- Fix A: use the ahead window only when it is at least half as fast as the fastest window; else the fastest (2 lines, 1 file).
- Fix B: test "is it a throw" against the fastest window of all, and use the ahead rule only to pick the direction (about 4 lines, 1 file).
- Or intended: the README row says the throw must go where you look.
- Note: the same code is copied in RSQ FnF and RSQ ShieldSaw (hand.zs:139-142 says so); those are other readers' mods.

## F4: Taking the ring fires whatever gun the other hand holds
- Kind: possible bug
- Where: hand.zs:893 (the other hand's primary fire is read from the player's command), hand.zs:935 (take the ring), hand.zs:959 (put the pin back)
- What the code does: the ring is taken, and the pin put back, on the other hand's trigger press near the ring. Nothing eats that press (the mod has no input handler), so it is also a normal trigger pull for that hand.
- Why it looks wrong: with a gun in the other hand (the grenade in the off hand from the Tactical Rig, or dual wield), pulling the pin costs a shot, at point blank, next to a grenade. The teeth route avoids it.
- Sure?: certain about the code. Whether it is felt needs a headset with a gun in the other hand.
- Fix A: while the other hand is within 12 cm of the ring, eat its fire key in an InputProcess and send the ring take as a network event (about 20 lines, 1 file; the way RSQ Wheel eats its presses).
- Fix B: take the ring with the other hand's secondary fire as well, so a player can choose the button that does not shoot (2 lines, 1 file).
- Or intended: the README keeps its limit: "The other hand's primary fire is still that hand's own trigger."

## F5: The mega blast's new ceiling fit never runs at default settings, and a roof beside the blast is not seen
- Kind: possible bug
- Where: flip.zs:73-79 (the 11-27 fit for the flipbook), explosions.zs:204 (Fit changes nothing where the ceiling over the blast point is sky), explosions.zs:421-422 and :503-505 (with Big Blasts Outdoors Only on, the mega plays only where the ceiling over the blast point is sky), CVARINFO.txt:67 (that row is on by default)
- What the code does: both tests look at the one sector the barrel stands in. By default the mega is only chosen when that sector has a sky ceiling, and in that case the fit returns "as played". So at defaults the only thing that made the mega smaller on 11-27 is Mega Explosion Size (0.6). The fit only acts with Big Blasts Outdoors Only off.
- Why it looks wrong: the owner's report was the mega "constantly clipping through ceilings". A barrel in a courtyard next to a building, or at the edge of an overhang, is "under sky" at its own spot, plays the full mega, and the wide frame still crosses the roofed sector beside it. Nothing measures that.
- Sure?: certain about the code. Whether clipping is still seen needs the headset: a chain of three barrels in an open yard, the third within 100 units of a roofed doorway.
- Fix A: for the flipbook, take the lowest non-sky ceiling at a few points round the blast (the frame's half width out, 4 to 8 points) and fit to that (about 15 lines, flip.zs and explosions.zs).
- Fix B: make "outdoors" stricter for the big ones: sky over the blast AND over a ring of points at the mega's half width, else #5 Snap as indoors (about 10 lines, explosions.zs).
- Or intended: the README says the mega plays wherever the barrel itself is under sky, at Mega Explosion Size.
