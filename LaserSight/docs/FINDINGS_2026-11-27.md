# RSQ LaserSight: findings from reading the code (2026-11-27)

Read at commit 692b3e53c. Every ZScript file LaserSight includes was read whole (zscript.txt and the files under
`zscript/rsqls/`; of the generated data, the table rows of `muzzles.zs`, `halo_gen.zs` and the VOXELDEF lumps only far
enough to know what they are), with CVARINFO, MENUDEF, MAPINFO, MODELDEF and CREDITS.txt. There is no KEYCONF. Nothing
was run: no rig, no headset. Each finding is a question for the owner. Nothing was changed.

Paths are inside `LaserSight/` unless they start with another folder. `sight.zs`, `beam.zs`, `learn.zs`, `hand.zs`,
`head.zs`, `muzzles.zs`, `sets.zs`, `bdbore.zs`, `a11y.zs`, `halo_gen.zs` and `rsmenu.zs` are in `zscript/rsqls/`.
"Old README" is `LaserSight/README.md` as committed at 692b3e53c (`git show 692b3e53c:LaserSight/README.md`).

Ordered by what a player would meet first. Wording and comment mismatches are at the end.

**The keys plan (design/KEYBINDS_PLAN.md:6) against the code:** the plan says LaserSight has no keys, and the code has
none: no KEYCONF lump, no InputProcess, no NetworkProcess, no binding lookup. The code does read each hand's primary
and secondary fire (sight.zs:157-158, learn.zs:81-82 and :94), only to time the beam after a shot and to learn what a
gun fires. It takes and acts on no press.

**What the code does not have at all:** a beam on anything that is not a measured gun. The beam is a rod placed from a
table measured per gun (muzzles.zs, sets.zs); a weapon with no row can only get the dot. F1 and F2 are both this.

## F1: A hand holding a saber, the whip, a glove or the ShieldSaw has no beam, so the open Wheel draws only its own thin beam on it (Show on Melee gives such a hand a dot, never a beam; no setting gives it a beam)
- **OWNER 2026-11-27 (asked through the Wheel, before this read): "Make the Wheel's beam thick" (Fix C). DONE in the Wheel: its own beam went from 0.12 to 0.4 units wide. This read confirms the cause he was told was likely.**
- Kind: other (the owner's report; the code does this on purpose)
- Where: sight.zs:518-519 (the test), sight.zs:928 (a beam needs a pose row from the table), sight.zs:657 and :1503-1504 (what "laser.beam" answers); Wheel/zscript/wheel/wr_q_shim.zs:1328 and :1365 (the Wheel draws its own beam when the answer is 0)
- What the code does: `bool measured = bt && bt.Find(w) >= 0 && !w.bMELEEWEAPON;` then `if ((w.bMELEEWEAPON || w.bCHEATNOTWEAPON) && !measured && !Flag("rsqls_show_melee")) return false;`. A weapon flagged MELEEWEAPON, or flagged CHEATNOTWEAPON and not in the beam table, gets no beam, no dot, no arc. Flagged MELEEWEAPON in this repo: the sabers (QuestSaber/zscript.txt:467), the whip (Whip/zscript/rsqwp/weapon.zs:45), the gloves (Melee/zscript/rsqml/gloves.zs:49). Flagged CHEATNOTWEAPON: the ShieldSaw (ShieldSaw/zscript/ssq/shield.zs:27), the Force hand, the hand grenade, the weapon sets' bare hand. With Show on Melee on the hand is live, but none of these has a row in the table, so it still has no beam: "laser.beam" answers 0 for it in every case.
- Why it looks wrong: with the Wheel open, a gun hand points with the laser's own beam and a melee hand points with the Wheel's thinner one. Two different pointers, by what you hold.
- Sure?: certain for the classes named. Brutal Doom's own fists, chainsaw and axe are not in this repo, so their flags were not read; none has a row in the table, so they cannot have a beam either way.
- Fix A: while the Wheel is open (its service wr_RigService "IsOpen", Wheel/zscript/wheel/zscript.zs:178), LaserSight draws a straight beam for a hand with no measured gun, from the controller along where the hand points, built from the segments the bent grenade beam already uses for unmeasured guns (sight.zs:905-917, LayArcBeam). "laser.beam" and "laser.line" then answer for that hand and the Wheel points along it. It moves once a tic, as the Wheel's own beam does (about 25 lines, 1 file).
- Fix B: the same straight beam at all times for any hand Show on Melee lets through, so Show on Melee means beam and dot (about 20 lines, 1 file; see F4).
- Fix C: leave LaserSight alone and make the Wheel's own beam as thick and bright as the laser's (the Wheel's code, the Wheel's reader).
- Or intended: the README says: "A hand holding a melee weapon gets nothing. With Show on Melee on it gets a dot, never a beam."

## F5: The trigger is only noticed while the gun is on a frame with no measurement, so a quick shot may still blink the beam off
- Kind: possible bug
- Where: sight.zs:153-161 (Busy notes the triggers and answers), sight.zs:699-700 (Busy is called only in the `else` branch, when the frame shown has no measured pose)
- What the code does: the 35 tic "keep the beam after a shot" clock is set inside Busy, and Busy runs only on tics when the gun shows an unmeasured frame. A trigger pressed and let go while the gun still shows measured frames is never noted. When the gun then reaches an unmeasured frame of the same shot (a pump, a recoil step), the clock is stale, Busy says yes, and the beam hides until a measured frame comes back.
- Why it looks wrong: the comment at sight.zs:143-150 says the beam holds for a second after a press of that hand's trigger. That is true only if the press and an unmeasured frame fall on the same tic.
- Sure?: likely in the code; unsure it is seen. It depends on whether a gun's first fire frames are in the table (the pump shotgun's SHTA 9 to 16 are not; its first fire frames could not be read here). A rig test settles it: tap the trigger as short as possible on the pump shotgun with Debug Log on and watch "straight" in the MASK line through the pump.
- Fix A: note both hands' triggers at the top of WorldTick every tic, and leave Busy to answer only (about 4 lines, 1 file).
- Or intended: the README row says the beam is kept "for 35 tics after that hand's fire was last seen held".
